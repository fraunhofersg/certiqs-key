# Claim-file format

This file is for contributors who write claim files; a reader of the
contracts wants `harness/contract-reading.md`.

This document specifies the file format of claims and modules. The checker
(`harness/check_claims.py`, with `harness/check_presentation.py` for the rules
marked **[presentation]**) is its executable form, and the two are kept in
step: a change to one is a change to the other in the same commit. The rules
marked **[separation]** are check 13 of §6. How a
contract reads (what goes where, titles, summaries, language) is
`spec/style.md`.

One claim is one file, with its dependencies declared inside it. A change is
therefore local, its re-review scope is computable, and the whole is still
assembled into one readable contract per module. The format follows the Lean
blueprint pattern (`uses`, a Lean name, a status per node) without its
toolchain, so a Lean name can be attached to any claim without changing the
structure.

---

## 1. Where claim files live

```
spec/modules/<module-id>/
  module.yaml              id, version, title, abstract, depends_on, submodules, order
  interface.yaml           inputs, outputs, parameters, thresholds (no claims: those are files)
  claims/<kind>-<slug>.tex one file per claim
  contract.tex             GENERATED by harness/assemble_contract.py; never edited
  contract.pdf             GENERATED from contract.tex; the review copy
  graphs/                  GENERATED graph index, DOT, SVG and overview PDF
  <submodule-id>/          a submodule: same layout, one level down, no further nesting
```

A submodule is a directory inside its core module with its own `module.yaml`
(`kind: submodule`, `id` is the bare directory name) and `claims/`. Its claims
may use the core's claims and anything the core's `depends_on` allows (it
inherits the list); the core's claims never use a submodule's. A core and its
submodules are assembled into one **contract**, which is the namespace in
which a `\ref` resolves and a `\label` must be unique.

No `\section` appears in a claim file, so a `\ref` to a section of another
document is never legal; such a document is named in prose or with
`\repodoc` (§4.3).

## 2. File naming and ids

- The file name is `<kind>-<slug>.tex`, where `slug` is lowercase letters,
  digits and hyphens and `kind` is one of:

  | kind | what it is |
  | --- | --- |
  | `thm`, `lem`, `prop`, `cor` | a theorem, lemma, proposition or corollary, with its proof |
  | `def` | a definition |
  | `ass` | an assumption: a checkable hypothesis, a leaf of the graph |
  | `rem` | a remark: mathematics about the claims around it |
  | `ex` | an example: a worked instance |
  | `fact` | an imported published result, quoted in this repository's notation |
  | `req` | a requirement: what the implementation must do, record or refuse |

- The claim's **label** is `<kind>:<slug>` and appears as `\label{...}` on the
  claim environment in that file.
- The claim's **id** is `<module-id>/<label>` for a core module and
  `<module-id>/<submodule-id>/<label>` for a submodule. Header entries may use
  the bare label within one module directory and use the full id across
  modules.
- An assumption also carries a **short id** `A-<UPPERCASE>`, unique across the
  repository. Code, run manifests and interface files refer to assumptions by
  short id.

## 3. The header

Each file begins with YAML front matter written as LaTeX comment lines, so
that LaTeX ignores it and the checker reads it:

```latex
% ---
% id: meat-core/thm:keylength
% kind: thm
% title: Key length from a lower bound on the rate
% summary: >-
%   A lower bound on the single-round rate gives a fixed-length key length,
%   with the penalty of [[lem:penalty]]. Consumers read the key length only
%   under the declared protocol assumptions.
% prominence: main
% status: draft
% uses: [def:declaration, lem:objective-block, protocol-compiler/def:bundle]
% assumes: [A-ATK, A-KEYREG]
% refs:
%   - "arqand2025meat, Thm. 3"
%   - "tomamichel2016finite, Eq. (12)"
% provenance: newly-derived
% implements: certiqs_key.meat.finitekey.keylength:key_length
% lean:
% ---
```

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | equals the id derived from the path |
| `kind` | yes | equals the kind in the file name; the environment matches it (§4) |
| `title` | yes | the claim's only title: the assembler prints it in the heading, and the environment carries none. A descriptive noun phrase of at most 70 characters as rendered, with no claim code of the internal test registries under `tests/oracles/` (C5, PC9, RC8, PR13, SA5, DA1) and no assumption short id **[presentation]**. No backslash outside `$...$` (an accented letter is written as itself, from the mapped set of §3.1), and inside `$...$` only the macros that the plain-title map `PLAIN_TITLE_MACROS` of `harness/contract_navigation.py` renders, the font wrappers of `PLAIN_TITLE_WRAPPERS` and the spacing commands, since the title is flattened to plain text for the PDF bookmarks, the graph labels and the graph index **[presentation]** |
| `summary` | yes **[presentation]** | the result in plain words, then its consequence (§3.1); non-normative |
| `prominence` | yes **[presentation]** | `main`, `standard` or `technical` (the criteria are `spec/style.md` §5); a claim without the field reads as `standard`. A remark or an example is never `main` |
| `status` | yes | `draft`, `verified`, `accepted`, `implemented`, `superseded` (§6, check 9) |
| `uses` | yes (may be empty) | claims whose statement or proof this one relies on. An edge here is a dependency: it takes part in the cycle check, in `--dependents` and in the effective status |
| `mentions` | optional | claims this one refers to without depending on them (a pointer, a forward reference to a consequence). Not a dependency. A mention may point into any module. Every entry is referenced in the body (§4.3) **[separation]** |
| `pending` | optional | labels this file references that belong to claims that do not exist yet; a `\ref` to one is legal, and the entry becomes an error as soon as a claim defines the label (move it to `uses` or `mentions`) |
| `assumes` | yes (may be empty) | short ids of the assumptions this claim rests on directly. A `\ref` to such an assumption needs no `uses` entry |
| `refs` | yes (may be empty) | `"<ref-id>, <locator>"` strings, split at the first comma; the ref-id is registered in `refs/index.json` and the locator is non-empty |
| `provenance` | yes | `published` (then `refs` is non-empty) or `newly-derived` (which may carry supporting `refs`: the derivation is here, the ingredients are cited) |
| `short_id` | assumptions only | `A-...`, unique repository-wide |
| `verification` | assumptions only, required | `never` or `partly`: whether the engine decides what a proof takes from the assumption (§3.2); `decided` and `discharged` are refused |
| `category` | assumptions only, required | the component the assumption is about, one of `source`, `receiver`, `laboratory` (a party's laboratory, its boundary with the quantum channel and the public messages), `channel-and-adversary`, `protocol-structure`, `local-randomness`, `post-processing`, `honest-model`, `supplied-artefact`, `numerical-trust` (the one vocabulary, `ASSUMPTION_CATEGORIES` in `harness/check_claims.py`; its order is the order a report groups by) |
| `presupposes` | assumptions only, optional | a YAML list, without repeats, of the roles a run must have for the assumption's text to hold; absent means none. Drawn from `trusted-source` (the run is in trusted-source mode), `sends` (a party's laboratory holds a trusted source whose emission enters the proof, trusted mode and d_A ≥ 2; read at the emitting row's party where the row names one, else some party sends), `setting` (a private per-round setting with at least two values exists at the station; at the row's station, or at some station for a party- or run-level row), `letters` (the declaration's letter alphabet X has at least two letters); the vocabulary is `ASSUMPTION_PRESUPPOSITIONS` in `harness/check_claims.py`. A sentence of the title, summary or `user_statement` that names a role either has an entry here or is conditioned (§6, check 14). There is no scope field: the run-tier rows already name the station or party they are emitted for, and a header repeating that would drift from the emitters |
| `affects` | assumptions only, required | a non-empty YAML list, without repeats, drawn from `secrecy`, `correctness`, `completeness`: what the assumption's failure puts at stake. Where the claim graph decides it, it agrees (§6, check 8) |
| `refines` | assumptions only, optional | the short id of the assumption this one narrows: another assumption, never itself, and the `refines` graph is acyclic. A member of a family stays self-contained |
| `user_statement` | required on an assumption; optional on every other kind but a definition, where it is refused | on an assumption, a longer plain-text reading that a user checks against their setup, which may say what to declare instead when it does not hold; on any other kind, a plain-text reading of the result for a user who is not a proof expert: what it guarantees or warns about, in words (§3.1). Non-normative; the statement wins |
| `implements` | optional | `python.module.path:symbol`; required at status `implemented`. A requirement carries it once its code exists, as may the definition or result whose object the symbol computes; a remark never carries it **[separation]** |
| `lean` | optional, may be empty | the Lean declaration name once one exists |
| `supersedes` | optional | id of the claim this one replaces |
| `notes` | optional | a current caveat a drafter needs ("deliberately weaker than X because Y"); never history, never normative |

A field not in this table is an error. The four assumption fields
`category`, `presupposes`, `affects` and `refines` are refused on every
other kind, and
`user_statement` on a definition, which asserts nothing a user relies on;
`category`, `affects` and `user_statement` are required on every assumption
(`ASSUMPTION_FIELDS_REQUIRED` in `harness/check_claims.py`). A
`user_statement` on a result, remark, requirement, example or fact is
optional: the key-rate report shows its security statement to users who are
not proof experts, such as experimentalists and certification labs, and the
plain reading it shows them lives with the claim it reads, so that it is
seen and changed beside the statement rather than kept as a run-tier copy
that would go stale.

### 3.1 Summaries and the other plain-text fields

A claim's `summary`, a claim's `user_statement`, a module's `abstract`
and a reading group's `abstract` (§5) are plain text, rendered into the
contract PDF and, all but `user_statement`, the graph index, and never into
mathematics. For all four:

- nonempty plain text: no TeX, no backslash, no dollar sign;
- Unicode only from the mapped set, `UNICODE_TEX` in
  `harness/contract_navigation.py`: the Greek letters, relations and arrows
  (≤ ≥ ≠ ≈ ≡ → ← ↔ ⇒ ↦), set symbols (∈ ∉ ⊆ ⊂ ∩ ∪ ∅), operators and
  delimiters (· × − ± √ ∑ ∞ ⌈ ⌉ ⌊ ⌋ ⟨ ⟩ ‖), typographic dashes and quotes, and
  Latin letters with diacritics, each mapped to the TeX that renders it. A
  character outside the set is added to the table with its TeX, never worked
  around;
- links: `[[label]]` names a claim of the same contract by its label (unique
  there, §4.3), `[[module/label]]` a claim by its full id, `[[A-XXX]]` an
  assumption by its short id. The target must exist. In the PDF a link
  renders as the linked "Proposition 7.3" inside the same contract, as
  `\xref` does (§4.3) for a claim of another contract, and as the short id
  itself for an assumption; in the graph index it is a Markdown link to the
  claim in its contract PDF. A link is not a dependency and needs no header
  entry.

A summary gives the result, then its consequence or role, in at most two
sentences (an abbreviation or a decimal number ends none) and at most 300
characters as rendered, a link counting as its rendered "Kind 7.3"
**[presentation]**. Every claim has one, remarks included **[presentation]**.

A `user_statement` has no sentence limit and at most 900 characters as
rendered, a link counting as its rendered "Kind 7.3" or short id. On an
assumption it is what a user checks against their setup. On any other kind
it reads the result for a user who is not a proof expert: what it guarantees
or warns about, in words, exact about what is and is not promised, linking
an assumption where it names one; a definition carries none. It changes in
the same commit as the claim's statement; an edit of it alone is editorial,
like a summary's, and a substantive review checks that it agrees with the
statement.

Whoever changes a statement, a proof or a claim's scope updates its summary in
the same commit and checks whether the group and module abstracts still hold.
An edit of summaries or abstracts alone is editorial: no mathematical review
round, no status change, no module version bump. Such prose cannot change a
claim by implication, since the statement, proof and assumptions remain
authoritative; whether it says what the claim says is judged by a reader, not
by a tool.

### 3.2 Whether the engine verifies an assumption

An assumption's `verification` field is the one place that says whether a
run rests on it unverified. Interface ledgers, code constants, golden ledgers
and the run record's never-verified marks follow it, and
`tests/unit/test_never_verified_agree.py` holds them to it. The criterion is the clauses of the assumption that a proof consumes:

- `never`: some clause a proof consumes (the security argument's or, for an
  honest-model premise, the completeness argument's) is decided by no code
  path on some route or input, so a run rests on it as an attestation. A clause the engine does
  decide beside it (a type check, a declared-data check) does not change
  this. Every ledger row of the assumption and every run record that carries
  it mark it never verified.
- `partly`: the engine decides every consumed clause on every route, and a
  module other than the assumption's owner decides some of them; the
  assumption's text says which part and where. A consumed clause that some
  route or input leaves undecided makes the assumption `never`.

An assumption is an unchecked premise, so these are the two values it
carries. A condition the engine decides from declared data on every route,
refusing when it fails, is not an assumption but a definition plus a
requirement, and a condition a theorem discharges is a lemma; the values
`decided` and `discharged` are refused.

The contract says in one sentence after each assumption whether the engine
verifies it, so a reader sees it without the header: the assembler
generates that sentence from the field (§7), and the body does not write it.

## 4. The body

### 4.1 Shape

After the header, the body is, in this order:

1. an optional **lead-in**: non-normative prose before the environment
   (motivation, the key idea, the link to the claim before). Mathematics is
   allowed; a `\label`, a numbered display, a `\term` and a macro definition
   are not **[presentation]**, and nothing may cite it;
2. exactly one **claim environment** matching the kind, carrying
   `\label{<kind>:<slug>}` and no bracketed title;
3. the **proof** where the kind requires one;
4. nothing else: no text between the statement and its proof, and none after
   the proof or the environment, apart from whitespace and comments
   **[presentation]**.

No `\section`, `\input` or preamble.

| kind | environment | proof |
| --- | --- | --- |
| `thm` | `theorem` | required (`proof` environment); its `uses` holds no remark and no requirement **[separation]** |
| `lem` | `lemma` | required; `uses` as for `thm` |
| `prop` | `proposition` | required; `uses` as for `thm` |
| `cor` | `corollary` | required; `uses` as for `thm` |
| `def` | `definition` | none; its `assumes` is empty (a definition asserts nothing that could be false: the claims that rest on a premise declare it), and its `uses` holds no remark and no requirement **[separation]** |
| `ass` | `assumption` | none; its `uses` holds only definitions and its `assumes` is empty; its body references only definitions and the assumption it refines (§4.3); some claim declares it (§6, check 8) |
| `rem` | `remark` | none; it carries no `implements` and is never `implemented`: a remark is mathematics about mathematics and has no code **[separation]**. A remark may use any claim |
| `ex` | `example` | none; other claims may `mention` an example but never `use` it; never `implemented` **[separation]** |
| `fact` | `fact` | none; `provenance: published` with a locator in `refs`, the symbol map and the hypothesis check in the body, `uses` only definitions (its hypotheses go in `assumes`). Other claims may `use` it |
| `req` | `requirement` | none; it may carry `implements`, and it may use any claim (for a requirement, `uses` reads "motivated by") |

A proof may be marked `\begin{proof}[Proof sketch]` while the status is
`draft`; a `verified` or later claim carries a full proof.

### 4.2 Statements

The content of the claim environment is the statement. It holds none of
`\textbf`, `\texttt`, `\verb`, `\url`, `\href` or `\repodoc`; no code
identifier (`certiqs_key...`) and no repository file name (`*.py`, `*.yaml`,
`*.md`, `*.json`); and `\iface` only in a requirement **[presentation]**.

### 4.3 References

- `\ref` and `\eqref` name a label of the same contract (§1) that this claim
  defines, or that a claim listed in `uses` or `mentions` defines, or the
  label of the assumption owning a short id in `assumes`, or a label listed in
  `pending`. Through `mentions` a reference to another claim's equation is a
  pointer; a proof step that leans on the equation's content is a dependency
  and needs `uses` (the drafter's judgement, the verifier's check). A label
  that a declared claim of another contract defines is never reached by
  `\ref`, even where the local contract happens to define the same label
  **[presentation]**.
- The statement of a theorem, lemma, proposition, corollary, definition,
  assumption or fact references no remark, requirement or example: no `\ref`
  or `\eqref` to a label such a claim defines and no `\xref` to one
  **[separation]**. A pointer to one stands in the lead-in or the proof, or
  goes where the target's generated "Used by" line already links back. The
  statements of remarks, requirements and examples point by design and are
  exempt.
- Every `mentions` entry is referenced in the body (lead-in, statement or
  proof) by a `\ref` or `\eqref` to a label it defines or by an `\xref`
  **[separation]**. A `[[...]]` link in a summary and a name in `notes` need
  no entry (§3.1) and do not count. With check 6, `mentions` is exactly the
  claims the body points at that are not in `uses`, `assumes` or `pending`.
- The body of an assumption, lead-in and statement, references by `\ref`,
  `\eqref` or `\xref` only definitions, the assumption itself and the
  assumption its `refines` names. It states a checkable condition, and a
  reader checks it without its consumers; a pointer to a consumer or a remark
  goes elsewhere, and the generated "Assumed by" line links the consumers.
- `\xref{<full id>}` names a claim of another contract. The target exists,
  lies in another contract, and is listed in `uses` or `mentions` or owns a
  short id listed in `assumes`. It renders as the target's kind, title and id,
  linked into that contract's PDF. A claim id is never written as
  `\texttt{<claim id>}` **[presentation]**.
- `\cref`, `\Cref` and the rest of cleveref are not available: cleveref is not
  loaded, and a reference writes its kind out ("Lemma~\ref{lem:x}").
- `\repodoc{path}` or `\repodoc{path#anchor}` names a file of the repository by
  its path from the root (letters, digits and `._-/`), which exists and lies
  outside the top-level directories `reports`, `state`, `tmp` and `context`.
  It renders as a link to the file showing its path. It stands in a lead-in or
  a proof, never in a statement **[presentation]**.
- `\cite[<locator>]{<bibtex_key>}` always has a locator, and the key is one
  that `harness/generate_bibliography.py` generates from `refs/index.json`.
- Every `\label` is unique within its contract.

### 4.4 Marking commands

- `\term[<gloss>]{<phrase>}` marks a phrase that a definition defines; it
  feeds the index of defined terms and the contract's Terms table, where the
  gloss is the phrase's one-line meaning (plain text, as a summary is)
  **[presentation: every `\term` has a gloss]**. It stands only inside the
  statement of a `def`, and each phrase is defined once per contract
  (compared ignoring case and spacing).
- `\tref{<phrase>}`, or `\tref[<defined phrase>]{<text>}` for an inflected
  form, is a use of a defined term: it renders as its text, linked to the
  definition, in this contract's PDF or in the one contract that defines it
  **[checked: it resolves to exactly one definition]**. In every section the
  first use of a multi-word term that the contract or a module it depends on
  defines is a `\tref`, except in the section that defines it
  **[presentation]**; single-word terms are linked where it helps.
- `\iface{<key>}` names an interface key or refusal string that a requirement
  binds; it renders in typewriter type **[presentation: only in `req`]**.

### 4.5 No counts of tool output in normative prose

A claim body, a `notes`, `summary` or `abstract` field, `interface.yaml` and
`design.md` name claims and name the command that computes a fact about the
graph (`check_claims --dependents <id>`, `--assumptions <id>`, `--status`);
they never restate a number that command returns ("declared by five claims",
"thirteen dependents"). Such a count is a hand-maintained mirror of a
generated view (PRINCIPLES.md §7): it is true when written and false once the
tree moves under it. A count that a claim states as its own content, such as
the number of cases a proof splits into or of clauses a definition lists, is
the claim's assertion and is checked by the verifier.

## 5. Module and submodule metadata

`module.yaml`:

```yaml
id: meat-core
kind: core            # or: submodule
version: 1.2.0        # bumped once per human-accepted batch
title: MEAT key-rate engine (meat-core)
abstract: >-
  What the module establishes, from which inputs, with which main results
  ([[thm:keylength]]), and the scope limits a reader must know first.
depends_on: [protocol-compiler]   # modules whose claims this module's claims may use
notation_version: "0.5.0"         # the spec/notation.md version this module pins
submodules: [frank-wolfe]         # assembly order of the submodules
reading_groups:                   # optional; see below
  - title: Declaration and key length
    start: def:declaration
    abstract: >-
      The section's storyline and its main result, [[thm:keylength]].
order:                            # assembly order of the claims
  - def:declaration
  - thm:keylength
  - ass:atk
  - req:refuse-inexact
```

Required are `id`, `kind`, `version`, `title` and `order`. In a submodule's
`module.yaml`, `depends_on` names sibling submodules by their bare name (the
sibling graph is acyclic) or other cores' modules and submodules by full id.

**Order.** `order` lists every claim of the module exactly once. Within it,
every `req` comes after every other claim; after the first `ass`, only `ass`
and `rem` claims stand until the first `req`, so that the assumptions close
the mathematics and the requirements form a part of their own; and when
reading groups are declared, the first `ass` and the first `req` each start a
group **[presentation]**.

**Reading groups** partition `order` into sections. Each entry has `title`
(nonempty plain text), `start` (a label in `order`) and an optional
`abstract`; no other keys. Starts are unique, follow the order, and the first
is the first claim of the order; a group extends to the next start or to the
end. Without groups a module has one group, "Claims". Groups are reading aids,
never dependencies; the same partition drives the contents, the PDF bookmarks,
the claim index and the graph overviews.

**Abstracts** follow §3.1. Every module, submodule and reading group has one
(checked over the tree by `tests/harness/test_summaries.py`): a module
abstract of five to eight sentences, a group abstract of two to six
(`spec/style.md` §4). The one-line captions of `spec/modules.yaml` are the
module map's labels, not a second introduction.

`interface.yaml` holds what is not a claim: `inputs`, `outputs`, `parameters`,
`declared_thresholds`, `error_terms`, `artifact_bindings` and `conventions`.
Claims and assumptions are files, never YAML entries. An assumption's ledger
row is a mapping in its owning module's `interface.yaml` whose `id` is the
assumption's short id and whose `machine_key` is the key under which
assumption ledgers and run records carry it; the assembler reads the key
from that row (§7), and any further field of the row is that interface's
own.

## 6. What the checker verifies (form only)

`python -m harness.check_claims [--repo .] [--module <id>]`
prints each finding as `path:line: message` and exits 1 on any. It checks:

0. **Modules**: each `module.yaml` parses, has the required fields, and its
   `id` and `kind` agree with its directory; `order` lists every claim exactly
   once; reading groups are well formed (§5); a submodule's `depends_on` names
   existing siblings, acyclically, or other cores' modules.
1. **Header**: it parses as YAML; required fields are present and unknown ones
   absent; `kind`, `status` and `prominence` come from their vocabularies, and
   a remark or example is not `main`; an assumption carries a
   `verification` from its vocabulary (§3.2) and no other kind carries
   one; `provenance` agrees with `refs`; a
   `fact` is `published`; summaries and abstracts are nonempty plain text
   whose every character is in the mapped set (§3.1). `category`,
   `presupposes`, `affects` and `refines` stand only on an assumption, and
   `user_statement` on any kind but a definition; `category` comes from its
   vocabulary, `presupposes` is a list from its vocabulary without repeats,
   `affects` is a non-empty list from its vocabulary without repeats,
   `refines` has the form of a short id, and
   `user_statement` is plain text in the mapped set of at most 900
   characters as rendered (§3, §3.1). An assumption carries `category`,
   `affects` and `user_statement`, and its `verification` is `never` or
   `partly` (§3.2).
2. **Identity**: `id` equals the path-derived id; the file name, `kind` and
   the environment agree; there is exactly one claim environment, it carries
   no bracketed title, and its `\label` is the claim's label; a proof is
   present exactly when the kind requires one.
3. **Edges**: every `uses` and `mentions` entry resolves to a claim, and every
   `assumes` entry to a short id; a cross-module `uses` goes only into a
   module listed in `depends_on` (or the parent core, for a submodule); a core
   claim never uses a submodule claim; no claim uses an example.
4. **Leaves**: an assumption's `uses` holds only definitions and its `assumes`
   is empty; a fact's `uses` holds only definitions; a definition's `assumes`
   is empty.
5. **Acyclicity**: the `uses` graph has no cycle.
6. **Undeclared dependencies**: every `\ref` and `\eqref` target is declared
   as §4.3 says; a `pending` entry whose target now exists is an error. An
   assumption's body references only definitions, itself and the assumption
   it refines (§4.3).
7. **Citations**: every `\cite` has a locator and a generated bibtex key;
   every `refs` entry names a registered ref-id.
8. **Short ids**: unique across the repository; every `assumes` entry names
   one; a `refines` entry names another assumption, not the assumption itself,
   and following `refines` from any assumption never returns to it. Every
   assumption is used: some claim lists its short id in `assumes`, or a used
   assumption refines it. `affects` agrees with the claim graph in the
   direction the graph decides: an assumption in the assumption closure
   (`--assumptions`) of a secrecy root lists `secrecy`, one in a correctness
   root's lists `correctness`, and one in a composition root's lists at least
   one of the two, so an assumption that affects completeness alone is in none
   of them. The roots are `SECRECY_ROOTS`, `CORRECTNESS_ROOTS` and
   `COMPOSITION_ROOTS` of `certiqs_key.domain.claim_closure`, the ones the run
   record reads; a root that names no claim is an error. The converse is not
   checked: a device premise reaches the key length through a run's route, not
   through claim edges, so an assumption outside every root's closure may
   still put secrecy at stake.
9. **Status coherence**: a claim with status `verified` or later has a full
   proof where one is required and no `pending` entries; `implemented`
   requires `implements`; `superseded` is exempt. The header `status` is the
   **local** judgement (this statement and this proof, given what the file
   uses and assumes). The **effective status** is computed: the minimum, on
   the ladder `superseded` < `draft` < `verified` < `accepted` <
   `implemented`, over the claim's transitive closure under `uses` and
   `assumes` (a short id resolved to its assumption, wherever it lives),
   itself included and `mentions` excluded. A claim may thus be accepted
   conditional on dependencies that are not accepted yet, and a module's batch
   is accepted when its claims' effective status is accepted. A substantive
   amendment drops the amended claim to the status its new review gives it;
   its dependents keep their header status and their effective status
   follows. A change to a claim's `affects`, `category` or `presupposes` is
   substantive: the claim drops to `draft` for one reviewer round.
10. **Body commands**: no cleveref command; every `\xref` names an existing,
    declared claim of another contract; every `\repodoc` an existing, citable
    file; every `\term` stands inside a definition's statement; every
    `\tref` resolves to the contract's own definition of its phrase or to
    the one other contract that defines it.
11. **Contract namespaces**: every `\label` and every `\term` phrase is unique
    within its contract.
12. **Links**: every `[[...]]` link of a summary, a `user_statement` or an
    abstract resolves.
13. **Separation** (the rules marked **[separation]**): what a contract
    asserts, what it points at and what binds code stay apart.
    `statement-ref-kind`: the statement of a theorem, lemma, proposition,
    corollary, definition, assumption or fact references no remark,
    requirement or example (§4.3). `uses-kind`: no theorem, lemma,
    proposition, corollary or definition lists a remark or a requirement in
    `uses` (§4.1). `remark-implements`: a remark carries no `implements`, and
    no remark or example has status `implemented` (§4.1).
    `mention-referenced`: every `mentions` entry is referenced in the body
    (§4.3).
14. **Presupposed roles**: each sentence of an assumption's title (one
    sentence), `summary` and `user_statement`, as rendered, that names a
    role needs a `presupposes` entry satisfying it, or a condition word.
    The role words are those of `ROLE_WORDS` in `harness/check_claims.py`,
    matched whole-word and case-insensitively: a sender's ("laser",
    "modulator", "prepares", "Trojan", "her source", "your source", "the
    physical source", "from Alice to Bob" and the rest listed there),
    satisfied by `sends` or `trusted-source`, and a private setting's
    ("private setting", "Bob's probe", "his probe" and the rest), satisfied
    by `setting`. The condition words are `CONDITION_WORDS`: "where", "if",
    "when", "whenever", "unless", "whose", "with a trusted source" and "in
    trusted-source mode". A finding names the sentence, the role word and
    both remedies. The check sees words, not meaning: whether a sentence
    needs the role, and whether its condition covers it, is the reviewer's.

**Presentation checks.** The rules marked **[presentation]** in this document
run in every run of `check_claims`, which prints every finding as
`path:line: presentation[<rule>]: message`, then a count per rule, and exits 1
on any.

**Separation checks.** The rules of check 13 are errors of every run of
`check_claims`, each printed as `path:line: separation[<rule>]: message`.

The checker also answers questions; the checks always run first, and a query
on a repository with errors still answers and exits 1. `--dependents`,
`--effective` and `--assumptions` take a claim id or an assumption's short
id, which stands for the assumption claim that owns it:

- `--graph out.dot` writes the `uses` and `assumes` edges with titles, ids and
  statuses (`.svg` or `.pdf` renders through Graphviz). With `--module`, local
  claims and one-hop boundary nodes; with `--focus <claim-id>`, the full
  prerequisite closure across modules. Mentions never become edges;
- `--dependents <id>` lists the transitive dependents of a claim, its
  re-review scope; for an assumption the claims declaring it in `assumes`
  count as dependents; claims that only mention the target are listed
  separately;
- `--status` prints the claims per module and status, each cell the header
  count with the effective count in parentheses;
- `--effective <id>` prints a claim's header status, its effective status and
  the claims that bind it;
- `--assumptions <id>` lists the claim's transitive assumption closure: every
  short id declared by the claim or its `uses` closure, with the claims that
  declare it. The claim-closure table a run record reads is the same walk.

Not checked, on purpose: whether a proof is correct, whether an edge is
necessary, whether an assumption is physically reasonable, whether a summary
says what its claim says. Those are the verifier's, the reviewer's and the
human's.

## 7. Assembly

`python -m harness.assemble_contract <module-id>` writes
`spec/modules/<module-id>/contract.tex`: a fixed preamble (article; the
mathematics packages amsmath, amssymb, amsfonts, amsthm, mathtools, dsfont,
braket and physics; xcolor, array, enumitem, graphicx, longtable, xurl,
needspace, hyperref and bookmark; for the assembler's own front and back
matter booktabs, xltabular, imakeidx, tcolorbox and refcount; the ten theorem
environments on one counter per section; the claim-body commands `\xref`,
`\term`, `\iface`; the mapped Unicode set of §3.1; `\input{../../macros}`
for the project macro set `spec/macros.tex`; no date, so that the output is
reproducible), one `\DeclareXref` line per claim of another contract that the
contract cites, then the front matter, the parts and the back matter below,
and the bibliography. A `\repodoc` is rewritten into a relative link.
`latexmk -pdf` compiles the result into `contract.pdf`, the human's review
copy, built by the same command and tracked next to the tex so that a reader
without the tooling can read it. `--no-pdf` skips the PDF on a machine without
TeX; it is then rebuilt before the change is committed.

The same command writes the module's statements digest, `digest.tex` and
`digest.pdf` beside the contract: every definition, fact, assumption, result
and requirement with the contract's numbers, without remarks, examples,
technical claims or proofs, each heading linked to its claim in the contract.
`python -m harness.assemble_contract --all` does every core module and then
the spec-wide overview, `spec/overview/overview.pdf` (the authored
`intro.tex` around a generated chain of every contract's main results and the
module map), rebuilding only what changed; its PDFs are byte-stable, so a
second run changes nothing.

The layout is `spec/style.md`'s. The front matter holds the module's title and
version, its abstract, one sentence saying that grey text is non-normative,
links to `design.md`, the graphs and the viewing instructions, the contents,
every `prominence: main` claim listed by number, title and summary, linked to
its statement, with its assumption closure (the digest holds the statements in
full), a table of every assumption the contract states or its claims assume,
with its `category` (blank when absent; once any assumption the table lists
carries one, the rows are grouped by category in the vocabulary's order,
assumptions without one last, and by short id within a category), the rows of `spec/notation.md` whose macros the claim bodies use, and the
Terms table (every `\term` of the contract and every term of another contract
it links with `\tref`, each with its gloss and its definition). The abstract
and the section introductions link the first use of each multi-word term the
contract defines to its definition. Part I holds the core's
reading groups as numbered sections without their requirements; Part II the
core's requirements, in sections named after the reading group each sits in
(no Part II when there are none); each submodule is one further part, its
abstract introducing it, its mathematics before its requirements. Sections are
numbered through the whole contract, and every claim within its section on
one shared counter ("Proposition 7.3"); `harness/contract_structure.py`
computes that structure for the PDF and the graphs alike. A section opens with
its group abstract and the claims of other contracts its claims use. A claim
is emitted as its summary (holding the named destination `claim-<id>`), a
numbered bookmark, its lead-in, the statement with its header title (framed
for a main result, a lighter heading for a technical one); for an assumption,
the generated sentence on its `verification` ("The engine does not verify
this assumption; a run that rests on it records it as unverified." for
`never`, "The engine decides part of this assumption; the rest is attested."
for `partly`; the one table is `VERIFICATION_SENTENCES` in
`harness/contract_render.py`); for every claim that carries one, its
`user_statement` as a "Reading:" paragraph; both in the non-normative grey;
a generated meta line (uses, or for a requirement what motivates it;
assumptions; for an assumption its category, `affects` and the assumption it refines when
present, the claims assuming it and its ledger machine key from the owner's
`interface.yaml`; the claims using it; provenance and citation; status and a
lower effective status; code; oracle pins from
`tests/oracles/claim_codes.yaml`), then its proof; text after the statement or
proof is printed, not dropped. The back matter holds the whitelisted fields of
the declared inputs and outputs of each `interface.yaml` (name, symbol,
presence and the claims its `fixed_by` or `locator` names), the claim index
with numbers, and the index of defined terms. Plain-text links render as §3.1
says; navigation titles come from the header metadata, their mathematics
flattened to plain text through the plain-title map (§3, `title`). The authored flowchart
stays in the non-normative `design.md`, linked from the PDF and the graph
index.

The same command writes `graphs/README.md` (the same prose beside navigation
links, numbered as the PDF is), the overview and group `.dot` and `.svg`
views, `graphs/claims.dot` and `.svg`, and `graphs/overview.pdf`, and
refreshes `spec/module-graph.dot` and `.svg` from the module registry's
declared core dependencies. The module map shows allowed dependencies, not
proof edges. The overview is a dependency matrix between sections (rows depend
on columns; U = uses, A = assumes, UA = both), linked from the PDF rather than
printed in it; `graphs/groups.svg` keeps the full arrow graph. Group views are
the contract's sections, named `group-NN-<topic>.dot`/`.svg` after the section
number and title, a namespace reserved for generated files; renaming or
removing a group removes its obsolete views. A claim node links both its
source and the rendered claim in its core's PDF, through the stable named
destination `claim-<id>` that `\xref` also uses.

`--check` writes nothing and exits 1 when a generated text differs from what
its inputs give, when an obsolete group view remains, or when a rendered
output is missing or older than its source (by modification time for
uncommitted files, by last commit otherwise, an output counting as current
when its source is byte-identical to the source at the output's commit). The
contract and digest PDFs are also compared with the shared macros and the
bibliography, and the digest with its contract;
`--no-pdf` skips every rendered-output check. Graphviz is an explicit build
dependency. [Viewing instructions](../harness/contract-reading.md) are linked
from the repository README, the dashboard, the PDFs and the graph indexes.
