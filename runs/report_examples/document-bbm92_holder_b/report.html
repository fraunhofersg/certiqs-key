The result

From n = 100,000,000 rounds the protocol, unless it aborts, outputs a key of ℓ = 40,193,071 bits: a key rate of 0.402 bits per round, ℓ divided by all n rounds, the rounds that give no raw key bit included. Its security parameter is ε = 1.86e-09. The accepted statistics were not checked against your declared model (its statistics are your honest model's predictions for your declared devices and you declared no constraint entry; Requirement "The check of the acceptance set against the feasible statistics"): that a state your declared devices admit can produce them, A-REACH, is yours to vouch for. The key length rests on a certified lower bound, hcert, on the attacker's worst-case uncertainty per round about the raw key. hcert is the solver's first-order bound formed again at its final points, from the data of the declaration it is formed on, with every arithmetic step exact or rigorously enclosed. It lies below that declaration's value by the claims alone, and the key length is computed from it exactly (Corollary "Key length from the certified bracket", Remark "What a certified number rests on"). It is formed on the reference companion: the declaration built from your receiver model, through the model's rigorous intervals, on every block the run handed those intervals for.

From the accumulated entropy to the key you gain (Theorem "Secrecy of the key from the accumulated entropy"):

  • The accumulated entropy, bounded below by n·hcert ≈ 40,193,730.4 bits (n = 100,000,000 rounds, hcert = 0.401937 bits per round).
  • Less 0 bits that error correction reveals (λEC, as declared).
  • Less a 30-bit hash for error verification (⌈log₂(1/ε_EV)⌉).
  • Less 630 bits that privacy amplification costs for a finite key (α/(α−1)·log₂(1/ε_PA)).
  • Plus one bit, a constant of the bound: its source's derivation adds two, and one of them pays for announcing whether error verification passed (Remark "The constant in the key length and the source's convention").
  • Rounded down to a whole bit, the key length is ℓ = 40,193,071 bits.
  • Authentication consumes kauth = 0 bits of pre-shared key per run (declared); an aborted run may consume as many.
  • You gain ℓ − kauth = 40,193,071 bits.

What the guarantee means

A run either aborts or outputs a key of ℓ bits that is a perfect key up to the security parameter ε: identical for both parties, uniform and independent of all the attacker holds, public messages included. One party may abort while the other gets a key. No test, whatever the attacker knows, tells the run's output from an ideal protocol's with advantage above ε = εPA + εEV + 2ε_auth. It holds against every attack, of any memory, if every premise in the run record holds, A-AUTH, A-CONFORM and A-FIXED included. A first-order run also needs its bound to hold, computed hlb ≤ hlow, which no premise covers (Remark "Exact real arithmetic in the first-order bound"). ε averages over aborted runs too. The criterion is composable. Separate executions provably add ε (Corollary "Security parameters of separate executions add"). Not every later use of the key is covered (Remark "One execution's security parameter and a reused key"). A run where both get a key nets ℓ − kauth bits; an abort uses up to kauth. Abort rates: Remark "Completeness covers the acceptance test only". Statement: Corollary "Security of the protocol and its net key".

This run's key length is certified (hcert, every arithmetic step exact or rigorously enclosed), so the clause on a first-order run's computed hlb does not apply to it.

The composable statement takes its authenticated classical channel from A-AUTH, whose own text says that no composable proof for this timing-aware channel is published yet; Wegman-Carter authentication with separate keys per direction approximates it.

Completeness. On this run an honest run fails the acceptance test with probability at most 1e-06 (ε*; its exact value). The completeness figure ε* bounds one thing only: the chance that an honest run, with no attacker and devices behaving as the declared honest model says, fails the acceptance test on its statistics. An honest run can also abort later: in error verification, when error correction leaves the two raw keys different, and in authentication. No result bounds those aborts, so an honest run's overall abort chance can exceed ε*. Whether your error-correction code reconstructs the key on honest runs is yours to check; it affects only how often you obtain a key. Completeness never affects the security parameter ε, which holds for every abort pattern (Corollary "Security of the protocol and its net key") and so says nothing about how often runs abort. Statement: Remark "Completeness covers the acceptance test only".

One execution. The security parameter ε covers one execution: one run of n rounds and its post-processing. It is not a per-round or per-bit figure, and it does not shrink when you repeat the protocol. Several executions are together secure with the sum of their ε (Corollary "Security parameters of separate executions add") under A-SEPARATE. The sum does not cover parameters chosen from an earlier run's data, such as the error-correction budget or the acceptance test. The conditions of A-SEPARATE include: (i) their number and parameters are all fixed before the first starts; (ii) they share no key material and no device state; (iii) their keys stay unused until the last has ended. Reusing key from an earlier run to authenticate the next is not covered either. Such a key enters only through the next run's declared authentication error εauth, counted twice, and the earlier run's ε does not by itself bound how far that key is from an ideal one. Statement: Remark "One execution's security parameter and a reused key".

Your QKD setup

What a round is

A round is one use of the protocol as declared, recording its own outcomes. How a time-tagged system cuts its detection record into rounds (time bins, coincidence windows, how the stations synchronise) is yours to choose, and your declaration must describe it. Every one of the n rounds counts: where your measurement has a no-click outcome, a time bin in which nothing clicks is a round with that outcome, not one to drop.

How you cut the record into rounds bears on these premises, each in full under Assumptions you vouch for:

  • A-SPEC: each round's recorded outcome is what the declared measurement gives, so a detection lost from its round or filed in another, or a no-click bin dropped, is a security matter.
  • A-EXACT: the declared efficiencies and dark-count probabilities are the true values for the rounds as you cut them.
  • A-MODES: no light outside the declared temporal modes (outside a window, say) reaches a detector.
  • A-PORT: a click probability that depends on the temporal mode (efficiency mismatch) is declared as mode-dependent loss.
  • A-THRESH: threshold detectors read once per gate, with no dead time, afterpulsing or timing jitter.
  • A-RHOM: one declaration covers every round.
  • A-ROUND: the same receiver behaviour in every round and no memory across rounds, such as dead time or afterpulsing across a boundary.
  • A-SEQ: the declared order of measurements and messages within a round, and each measuring party completing one round's measurement before the next round's.
  • A-LAB: no timing or synchronisation signal reveals a party's records, and only the declared inputs influence a measurement, not a clock or trigger line from the untrusted source.
  • A-FIXED: the number of rounds and the acceptance test are fixed before the run.
  • A-ALPHABET: all n rounds are in the record (the acceptance test is evaluated on all n rounds); a measured round missing from it, a lost time tag or no-click bin included, leaves the counts wrong and is a security matter under A-SPEC and A-CONFORM.

Protocol

  1. Rounds: The protocol runs n = 100,000,000 rounds. See What a round is above. Record: /payload/config/rounds.
  2. Source: In every round the untrusted source delivers one system to each station; see Source below. Record: /payload/compiled/source.
  3. Measurement: Each round is measured at Alice's station (element-graph) and Bob's station (element-graph); see the stations below. Record: /payload/stages/stations.
  4. Public choice (test coin): At Alice's station, a public choice is drawn: gen with probability 0.875, test with probability 0.125. The test fraction is 0.125. Record: /payload/compiled/public/choice_weightings/0.
  5. Announcements: First Alice announces one of gen:Z, gen:X, gen:nc, gen:mc, test:nc, test:H, test:V, test:D, test:A, test:mc; then Bob announces one of Z, X, nc, mc, H, V, D, A. Record: /payload/compiled/public/transcript.
  6. Sifting and key map: A round gives a raw key bit when its announcements pass sifting: 8 of the 72 combinations of readouts map to a key bit, the rest are discarded. Bob holds the key over the alphabet 0, 1. Key bases: ZX. Record: /payload/compiled/public/key_map.
  7. Acceptance test: The parties estimate the acceptance statistics on the whole run and abort unless they pass; see Acceptance test below. Record: /payload/stages/acceptance_construction.
  8. Error correction: One-way error correction; its transcript leaks λEC = 0 bits, which the key length deducts. Record: /payload/config/parameters/lambda_ec.
  9. Error verification: The parties compare a hash of the corrected keys (failure probability εEV = 9.31323e-10); the key length deducts 30 bits for it. Record: /payload/stages/key_rate/deductions/error_verification.
  10. Privacy amplification: A two-universal hash shortens the corrected key to ℓ = 40,193,071 bits, secret except with probability εPA = 9.31323e-10. Record: /payload/stages/key_rate/key_length.

The run records one acceptance value per round, from 79 outcomes, and accepts only if the observed frequency of every outcome lies in the box of intervals built around the honest model's probabilities (endpoint rule bernstein). An honest run fails it with probability at most 1e-06 (ε*), within your completeness budget of 1e-06 (the completeness parameter εcomp you allow). How the number was computed

How the number was computed

Over n rounds the attacker's uncertainty about the raw key accumulates to n times the per-round bound hlow, less a term for how unlikely the acceptance test is to pass, which cancels over all runs; the bound hlow holds over every attack compatible with your declared devices and with passing statistics. Subtracted are the error-correction transcript of λEC bits, the verification hash of ⌈log₂(1/ε_EV)⌉ bits and a finite-size penalty of α/(α−1)·log₂(1/ε_PA) bits; one bit is added back. The remaining key of ℓ bits is secret, counted over all runs: it is within the secrecy parameter εPA of a uniform key independent of the attacker's memory and every public message. It is proved for a finite-memory attacker receiving every signal at once; Corollary "Security of the protocol and its net key" covers every attacker. The Rényi order α in (1, 2) is fixed before the run (A-FIXED) and changes the key's length, never its secrecy. Statement: Theorem "Secrecy of the key from the accumulated entropy".

The certified key rate is the best of a few brackets, each formed from enclosures of the gradient at a point the search found, with every arithmetic step from the declaration's data exact or rigorously enclosed. It is a lower bound on the minimum hlow of the declaration it is formed on, and the key length built from it is secret and correct under the same premises as the first-order key length: the declaration's modelling premises remain, but no premise about how a number was computed is added, the key length itself being computed exactly, its one logarithm enclosed until the integer part is decided. It is not a bound on any other declaration, so a run formed on the snapped declaration still rests where its record says on the premise that the device measures the snapped family. Statement: Corollary "Key length from the certified bracket".

The key length is certified: the first-order bound was formed again at the solver's final points from the data of the declaration it is formed on, every arithmetic step exact or rigorously enclosed, so no premise about how a number was computed is added; the premises of the run remain (Corollary "Key length from the certified bracket", Remark "What a certified number rests on"). It is formed on the reference companion: the declaration built from your receiver model, through the model's rigorous intervals, on every block the run handed those intervals for.

Security claims

Security claims

Security statement

  • Corollary "The first-order bound on the reference companion": At any points, such as those of a search on the snapped declaration or of one continued on the companion, the bracket formed with the reference companion's objective, gradient, entries and linear minima bounds the companion's value from below; its key length is the reference model's.
  • Corollary "Key length from the certified bracket": The largest bracket formed by Lemma "The certified bracket from enclosures of the gradient" over finitely many points is a first-order bound of Theorem "The estimate and the first-order lower bound", so it is at most the value of the declaration it is formed on and gives that declaration's fixed-length key length exactly as hlb does.
  • Corollary "Key length on a reference companion from the certified bracket": On a reference companion, the best certified bracket, formed over its enclosed measured family as Lemma "The certified bracket over a measured family known through enclosures" allows, gives the key length of the protocol whose declaration is the companion, as the first-order bound on the companion does.
  • Corollary "Key length from any lower bound on the value": Any h ≤ hlow may replace hlow in the key-length bound through max{0, h}, with the same security statement. This is where every solver obtains its key length; a bound h ≤ 0 yields no positive key when εEV < 1.
  • Corollary "Security of the protocol and its net key": Secrecy and correctness compose to (εPA + εEV)-security with honest authentication; over an authentication scheme within εauth that consumes kauth bits of pre-shared key, the protocol is (εPA + εEV + 2ε_auth)-secure; when both parties output a key, its net key gain is ℓ − kauth bits.
  • Theorem "Secrecy of the key from the accumulated entropy": For a Rényi order α in (1, 2), a key of length ℓ ≤ n·hlow − λEC − ⌈log₂(1/ε_EV)⌉ − α/(α−1)·log₂(1/ε_PA) + 1 is εPA-secret on the accepted state at every all-at-once finite-register attack the reduction chain carries onto the round model (A-LINK). Corollary "Security of the protocol and its net key" extends it to every attack.
  • Lemma "Correctness from error verification": In the fixed-length post-processing model the two parties accept with different keys with probability at most εEV, for every attack and every output length. It is the correctness half of the protocol's security.

Per execution

  • Remark "One execution's security parameter and a reused key": One execution's parameter covers one run, and separate executions that share no key add their parameters (Corollary "Security parameters of separate executions add"). A reused authentication key enters through εauth, charged twice, and the earlier run's parameter does not bound its distance in general.
  • Corollary "Security parameters of separate executions add": N executions that share no key and no device state and leave their keys unused until all have ended, run against one adversary, are together (ε_1 + ... + εN)-secure for the joint ideal map. A key reused from one execution in another is not covered.

Completeness

  • Requirement "The reported completeness figure": The engine reports ε* itself on the exact rule evaluated by its closed forms, and otherwise the figure its route's row names: the allocation sum or an upward-rounded evaluation of the tails clamped at the budget. It never reports a downward-rounded figure.

Limitations

  • Remark "Completeness covers the acceptance test only": The completeness parameter ε* of the statistics module bounds an honest run's failure of the acceptance test only. Aborts in error verification and in authentication are bounded by no claim, so ε* does not bound the honest abort probability of the whole protocol.
  • Remark "The declared measurement as a premise of the rate": A tiny change of the declared measurement can move the key rate by many bits per round, so the model is a premise of the rate. Where a handed reference's companion counts and the key length is formed on it, the snap only steers the search; nothing bounds model to device.
  • Remark "One execution's security parameter and a reused key": One execution's parameter covers one run, and separate executions that share no key add their parameters (Corollary "Security parameters of separate executions add"). A reused authentication key enters through εauth, charged twice, and the earlier run's parameter does not bound its distance in general.

Glossary
  • A (the letter): The report uses the letter A in four ways: party A of the declaration (Alice); system A, the declaration's per-round letter on that party's side; a detector port named A (as among BBM92's ports H, V, D and A); and the prefix of a premise's short id (A-LAB, A-SPEC). Which is meant follows from where it stands. See Definition "The protocol declaration as the MEAT core reads it".
  • acceptance map: An input of some templates (BBM92's among them): how finely the public announcements are grouped into the acceptance values the test checks. Every announcement pair its own value (pair-resolved), test rounds grouped by announced bases (announcement-resolved), or key rounds, matched-basis test rounds as ok or error, and one discard value for everything else (merged-discard).
  • acceptance test: The test every run applies to its statistics: each round records one acceptance value, and the run continues only if the frequency of every value lies in an interval (together, the box) around the honest model's prediction. See Definition "The construction map".
  • acceptance value label: An acceptance value as the protocol document names it. A document may name its values freely (key, ok, err); some, BBM92's among them, write the round's kind and then the two parties' announcements joined by a bar, in the order the document writes them. There gen:Z|X is a generation round in which the party written first announced Z and the other X, so no key; the key rounds record gen. See Assumption "An acceptance value recorded in every round".
  • Alice: The name the report gives party A of the declaration. A party may send, measure, or both: in a prepare-and-measure protocol Alice usually sends, in an entanglement-based one she measures at a station; the run's record says which. Where a premise speaks of Alice's letter or of system A, it means the party the declaration assigns A to: Alice, unless the party partition says otherwise. See Definition "The protocol declaration as the MEAT core reads it".
  • alice_transmittance: Probability that Alice's photon of a pair reaches her station. The instance's parameter model.alice_transmittance (Alice's transmittance); its value on this run is under Your inputs.
  • binding: A value of this run that an assumption is about, for example the εauth you declared for A-AUTH; shown under the assumption so that you know what exactly you vouch for.
  • Bob: The name the report gives party B, the other of the declaration's two parties. Like Alice, he may send, measure, or both; on most protocols he measures at one or more stations. Which he does on this run is read from its record, which also says which party holds system A. See Definition "The protocol declaration as the MEAT core reads it".
  • bob_transmittance: Probability that Bob's photon of a pair reaches his station. The instance's parameter model.bob_transmittance (Bob's transmittance); its value on this run is under Your inputs.
  • budget: An error probability (an ε) that you choose before the run. The secrecy, error-verification and authentication budgets εPA, εEV and εauth make up the security parameter ε. The completeness budget εcomp is not part of ε: it is the largest ε* you allow and bounds only how often an honest run fails the acceptance test. The configuration keys keep the word (completeness_budget). See Corollary "Security of the protocol and its net key".
  • catalogue entries: The kinds of optical component of the receiver module's catalogue that the declared receiver uses, by entry number, for example C1 beamsplitter, C2 polarising beamsplitter, C3 retarder (a wave plate); the catalogue lists C1 to C10.
  • certified bound: The first-order bound formed again at the solver's final points from the declared data, every arithmetic step exact or rigorously enclosed: a lower bound on hlow that rests on the claims and the modelling premises and on no premise about floating-point arithmetic. Where a run reaches it, the key length is computed from it, exactly. See Corollary "Key length from the certified bracket".
  • channel modes: The input modes of a receiver that the channel, and so the attacker, can populate; the photon-number blocks are over these modes.
  • Choi: A way of writing a quantum channel as one operator; the solver states its optimisation over operators in that form.
  • completeness: How often an honest run, with no attacker and devices behaving as modelled, aborts. It never affects the security parameter ε, which holds for every abort pattern. See Remark "Completeness covers the acceptance test only".
  • composable: The kind of security statement the guarantee is: no test, whatever the attacker knows, tells the run's output from an ideal key exchange with advantage above ε. Later uses of the key build on such a statement, but this contract proves only that separate executions add their ε, not that every later use of the key is covered. See Remark "One execution's security parameter and a reused key".
  • constraint entry: A constraint a declaration places on the states it admits, beyond the declared marginal. A run whose declaration carries an entry you declared is checked by the statistics check unless that check is switched off (the inputs table says whether it ran); entries the compiler or a reduction derives do not by themselves call for it. See Requirement "The check of the acceptance set against the feasible statistics".
  • dark count: A detector click with no photon arriving. Its declared probability per detector and round enters the measurement model.
  • declared tolerance τ: The ceiling on the defects of the run's own data that the snap may repair before solving.
  • detection efficiency: The probability that a detector clicks on a photon that reaches it.
  • digest: A hash that identifies the content of a file, an artefact or the configuration: the same digest means the same content.
  • effective status: The lowest review status over a claim and everything it rests on; a claim accepted on its own is only as reviewed as its weakest premise.
  • element graph: A receiver declared by its optical elements (beamsplitters, wave plates, polarising beamsplitters) and detectors; the engine computes the measurement from them. See Definition "Compilation of a declared element graph".
  • emitted by: The module of the engine whose result rests on the assumption on this run, with the station it was emitted at (station0, station1, ...).
  • endpoint rule: How the acceptance test sets the ends of each outcome's interval: the exact binomial quantile rule (exact) or the closed-form Bernstein rule (bernstein).
  • estimate: The value of the objective at the point the solver returned. It claims no bound: that point is feasible only within a window, so the estimate need not lie above the true minimum hlow. No key length is computed from it.
  • evaluated off its snap: Said of a moved snap block when no number the key length is computed from reads the rounded block: the bound is formed on your receiver model at the points the solver found on the rounded measurement. Such a block rests on your receiver model, not on A-SNAP. See Definition "A reference handed beside a snap; a block evaluated off its snap".
  • exact window: Above the photon cutoff N, up to a declared depth m*: the photon numbers at which the multi-click bound takes the larger of the analytic bound and the block's smallest eigenvalue, computed by a floating-point eigensolver less a declared slack εeig. The computed value is trusted under A-EIG.
  • feasible state: A state the declaration admits: block-diagonal and normalised, with the declared marginal and constraints. hlow is an infimum over the feasible states whose statistics pass the acceptance test.
  • first-order bound: A lower bound on hlow from the tangent planes of the objective at the solver's steps. Its proof is exact, and the minima it uses are bounded from below in exact arithmetic, not taken from the solver; its objective and gradient are computed in floating point with no bound on their numerical error. Stopping early makes it looser, not invalid. The key length uses it where the run is not certified. See Theorem "The estimate and the first-order lower bound".
  • flag: A one-dimensional sector of the squashed model that stands for one outcome of the receiver above the photon cutoff.
  • Frank-Wolfe: The solver's iterative method: each step minimises a linear approximation of the objective over the feasible set and moves toward that point. See Theorem "The estimate and the first-order lower bound".
  • Frank-Wolfe gap: The objective at one solver step minus that step's tangent-plane bound (fw run: the last step; candidate search: the best contributing one). A convergence diagnostic: it reads the point the solver returned, which nothing verifies, so it is no proven bound. See Remark "Two reported numbers and one first-order claim".
  • generation and test rounds: gen is the acceptance value of a round whose announcements pass sifting, so that it may give key. Where a public test coin exists (as in BBM92) it makes each round a generation round (gen), which may give key, or a test round (test), in which both parties announce their full outcome. Every round of either kind records one acceptance value.
  • geometry (acceptance set): The engine's name for the shape of the acceptance set it built; a box of intervals is a polytope.
  • hlb: The first-order lower bound on hlow: the best bound over the steps that passed the first-order checks. It is proved in exact arithmetic, its linear minima bounded exactly, and computed in floating point, so a computed hlb can exceed hlow. A first-order run computes its key length from max{0, hlb}; a certified run computes it from the certified bound hcert and records hlb beside it. See Theorem "The estimate and the first-order lower bound".
  • hlow: A lower bound on the attacker's per-round uncertainty about the raw key, at the chosen α, over every attack compatible with your devices and with statistics that pass the acceptance test.
  • honest envelope: The set of per-round outcome probabilities an honest run is declared to stay within (A-HON-ENV). With a single honest model, as on most runs, it is that model's one law. See Assumption "Honest rounds inside a declared envelope".
  • honest model: The model of what an honest run looks like. It sets the acceptance test and the expected statistics; it never affects the security parameter ε, which holds for every abort pattern.
  • iid_honest_rounds: The acceptance construction's tag for its honest model. In its simplest form the honest rounds are independent and identically distributed with one declared law (A-HON); A-HON-ENV, where a run lists it, lets each round's law vary inside the declared envelope. See Assumption "Honest i.i.d. rounds".
  • input radius: For an enclosed reference, the largest radius of the enclosures of the irrational inputs (square roots, trigonometric values) from which its centres were computed exactly.
  • kauth: The bits of pre-shared key the authentication uses per run; the net key gain is ℓ − kauth. See Assumption "Authentication of the classical channel by a keyed scheme".
  • kept (snap block): A snap block is kept where your model gives it exactly on the grid, so the snap changes nothing there; every other block is moved.
  • key bases: The matched bases of a generation round that give key.
  • key length ℓ: The number of secret key bits one run outputs, after deducting error correction, error verification and the finite-size cost of secrecy. See Theorem "Secrecy of the key from the accumulated entropy".
  • key map and sifting: Sifting decides from the public announcements which rounds give key; the key map sends each kept round's readout to a key bit. See Theorem "Announcement locality, sifting and party computability".
  • largest radius: For the reference handed beside a snap, the largest radius of the rational intervals that enclose its matrix entries: zero where the reference is exact.
  • letter: The per-round value on Alice's side of the declaration (system A): in a prepare-and-measure protocol, the signal she prepares. A declaration with one letter uses no clause a premise makes for two or more letters. See Definition "The protocol declaration as the MEAT core reads it".
  • machine key: The stable identifier under which the engine records an assumption.
  • mc: The outcome "more than one detector clicked" in the same round.
  • mean_pairs: Mean number of photon pairs the SPDC source emits per round, summed over both polarizations. The instance's parameter model.mean_pairs (Mean pairs); its value on this run is under Your inputs.
  • nc: The outcome "no detector clicked".
  • net key length: The key length minus the kauth bits of pre-shared key the authentication consumed: what the run gains. See Corollary "Security of the protocol and its net key".
  • oracle: The solver library the engine calls for each linear minimisation (QICS, through its sector Choi adapter). Its answers steer the search only; see LMO.
  • party local view: How each station's multi-click constraints enter the analysis on a licensed route: as operator inequalities (operator) or only their scalar consequences (licensed_scalar). It has no effect on the encoded route.
  • photon cutoff N: The largest photon number the receiver model treats exactly; higher photon numbers are bounded rather than modelled, so a pulse of more photons is still covered, through that bound (see squashed target POVM).
  • photon-number block: The part of a measurement acting on pulses of exactly m photons; m=0 is the vacuum, m=1 one photon.
  • POVM: A measurement written as one positive operator per outcome; the probability of an outcome is the trace of its operator times the state.
  • QBER: The quantum bit error rate: the fraction of key rounds in which the two parties' raw key bits differ.
  • reference (snap): Your declared receiver model, computed exactly (exact) or known through rigorous rational intervals (enclosed). The snap starts from it where it is exact, and the run hands it beside the snap so that the key length can be computed from it.
  • reference companion: Your receiver model put through the same reductions as the rounded measurement, without that rounding, its rows relaxed outward by their floating-point rounding and the model's intervals. A block not handed is carried rounded; with none handed, it is the reduction's exact construction before its own rounding. The run takes its first-order bound there and never solves it. See Corollary "The reference companion of a reduction instance".
  • review status: A claim's review stage, lowest first: superseded (replaced); draft (not yet through an independent review, sent back by one, or substantively amended since); verified (passed an AI model's adversarial review of the written artefacts, not the author's reasoning; not yet accepted by a person); accepted (by the project's human owner); implemented (accepted, its code too). Not a hardware check.
  • round: One use of the protocol as declared, which records its own outcomes. How a time-tagged system cuts its detection record into rounds (time bins, coincidence windows, how the stations synchronise) is your choice, and your declaration must describe it; What a round is, before the protocol's steps, names premises of this run that the cut bears on.
  • route (encoded, licensed): How the reduction squashes the receiver: the encoded route keeps each outcome's lower bound above the cutoff (its weight pv) in the target and adds no constraint; the licensed route uses one flag per outcome and adds a licensed constraint.
  • sector: One block of a block-diagonal operator, named by a sector map.
  • setting: A probe setting of a receiver; "off" is the setting with no probe light. A receiver without a probe has this one setting only, so on such a station "setting off" names its one measurement, not a switch. See Definition "Probe declaration".
  • snap: Before solving, the declarer (your instance, or a reduction for what it emits) moves each measurement onto a grid of exact numbers of the same shape. A block your model gives exactly on the grid is kept; every other block is moved, and rests on A-SNAP unless it is evaluated off its snap.
  • solver status: How the solver's search for a good point stopped, not whether the bound holds; the key length uses only steps that passed the first-order checks. See Requirement "Withdrawal of the first-order bound".
  • source mode: Whether the security analysis trusts the source. A trusted source's declared states enter the proof; an untrusted source is the attacker's, and its honest model only predicts the statistics.
  • SPDC: Spontaneous parametric down-conversion: a source of entangled photon pairs whose emission includes multi-pair events; one of this instance's honest models.
  • squashed target POVM: The finite-dimensional measurement the security proof works with; the reduction proves that analysing it covers your receiver.
  • strict option: The run setting strict_snaps: on, the run refuses wherever a moved block or emission sector would rest on A-SNAP, and reports no key length that rests on it, and the certified evaluation does not fall back to the rounded measurement where your receiver model certifies no point; off, the default, such a block is disclosed. See Requirement "Snaps of a measurement family: kept, or moved and disclosed".
  • temporal mode index: The reserved temporal or spectral index of every optical mode label; it takes a single value in a run and is not the declared tolerance τ.
  • test fraction: The probability that a round is a test round, in which both parties announce their full outcome.
  • transmitter: The engine module that models the source side of the protocol. With a trusted source it carries the source's declared states and their premises (A-ENS, A-SRC, or A-WCP for a decoy source); with an untrusted source it carries no source premise. On every run it carries its part of the sequential round order, A-SEQ.
  • visibility: Visibility v of the entangled pair: matched-basis bits disagree with probability (1 - v)/2. The instance's parameter model.visibility (Visibility); its value on this run is under Your inputs.
  • withdrawn step: A solver step whose first-order bound was withdrawn because a hypothesis failed or was not established; it contributes no bound. See Requirement "Withdrawal of the first-order bound".
  • x0: The one letter of this declaration's system A, which is one-dimensional here: with the untrusted source, every measurement of this protocol is made at a station, so A carries a single letter, of weight 1, that the proof does not use.
  • α (Rényi order): A parameter of the proof, not of your device: any value in (1, 2) fixed before the run gives a valid key length, and the choice changes only how long the key is, never its secrecy. See Theorem "Secrecy of the key from the accumulated entropy".
  • ε (security parameter): The bound on how far one run's output can be told from an ideal key exchange: ε = εPA + εEV + 2ε_auth. It covers one execution. See Corollary "Security of the protocol and its net key".
  • ε* (completeness): A bound on the chance that an honest run fails the acceptance test; it covers that test only, not later aborts in error verification or authentication. The completeness budget is the largest ε* you allow. See Theorem "The completeness bound".
  • εauth: The error of the authentication of the classical messages, which you declare, including, for a key from an earlier run, its distance from an ideal key; it is counted twice in ε. Zero asserts a channel that is itself authenticated. See Assumption "Authentication of the classical channel by a keyed scheme".
  • εEV: A bound on the chance that both parties accept the run with different keys; error verification compares a hash of ⌈log₂(1/ε_EV)⌉ bits. See Lemma "Correctness from error verification".
  • εPA: The secrecy error of privacy amplification: how far the key may be from uniformly random and independent of everything the attacker holds. See Theorem "Secrecy of the key from the accumulated entropy".
  • λEC: The number of bits the error-correction transcript reveals; the key length deducts it in full. You declare it; with an estimate file beside the record the report shows how it was chosen. See Assumption "Dedicated key register and one-way reconciliation".
