What the guarantee means

A run either aborts or outputs a key of ℓ bits that is a perfect key up to the security parameter ε: identical for both parties, uniform and independent of all the attacker holds, public messages included. One party may abort while the other gets a key. No test, whatever the attacker knows, tells the run's output from an ideal protocol's with advantage above ε = εPA + εEV + 2ε_auth. It holds against every attack, of any memory, if every premise in the run record holds, A-AUTH, A-CONFORM and A-FIXED included. A first-order run also needs its bound to hold, computed hlb ≤ hlow, which no premise covers (Remark "Exact real arithmetic in the first-order bound"). ε averages over aborted runs too. The criterion is composable. Separate executions provably add ε (Corollary "Security parameters of separate executions add"). Not every later use of the key is covered (Remark "One execution's security parameter and a reused key"). A run where both get a key nets ℓ − kauth bits; an abort uses up to kauth. Abort rates: Remark "Completeness covers the acceptance test only". Statement: Corollary "Security of the protocol and its net key".

The composable statement takes its authenticated classical channel from A-AUTH, whose own text says that no composable proof for this timing-aware channel is published yet; Wegman-Carter authentication with separate keys per direction approximates it.

It holds for each point that output a key, separately, with that point's own ε (the points).

Completeness. The completeness figure ε* bounds one thing only: the chance that an honest run, with no attacker and devices behaving as the declared honest model says, fails the acceptance test on its statistics. An honest run can also abort later: in error verification, when error correction leaves the two raw keys different, and in authentication. No result bounds those aborts, so an honest run's overall abort chance can exceed ε*. Whether your error-correction code reconstructs the key on honest runs is yours to check; it affects only how often you obtain a key. Completeness never affects the security parameter ε, which holds for every abort pattern (Corollary "Security of the protocol and its net key") and so says nothing about how often runs abort. Statement: Remark "Completeness covers the acceptance test only".

One execution. The security parameter ε covers one execution: one run of n rounds and its post-processing. It is not a per-round or per-bit figure, and it does not shrink when you repeat the protocol. Several executions are together secure with the sum of their ε (Corollary "Security parameters of separate executions add") under A-SEPARATE. The sum does not cover parameters chosen from an earlier run's data, such as the error-correction budget or the acceptance test. The conditions of A-SEPARATE include: (i) their number and parameters are all fixed before the first starts; (ii) they share no key material and no device state; (iii) their keys stay unused until the last has ended. Reusing key from an earlier run to authenticate the next is not covered either. Such a key enters only through the next run's declared authentication error εauth, counted twice, and the earlier run's ε does not by itself bound how far that key is from an ideal one. Statement: Remark "One execution's security parameter and a reused key".

What a round is

A round is one use of the protocol as declared, recording its own outcomes. How a time-tagged system cuts its detection record into rounds (time bins, coincidence windows, how the stations synchronise) is yours to choose, and your declaration must describe it. Every one of the n rounds counts: where your measurement has a no-click outcome, a time bin in which nothing clicks is a round with that outcome, not one to drop.

How you cut the record into rounds bears on these premises, each in full under Assumptions you vouch for:

  • A-SPEC: each round's recorded outcome is what the declared measurement gives, so a detection lost from its round or filed in another, or a no-click bin dropped, is a security matter.
  • A-IDEAL: exactly one qubit reaches the receiver in each round.
  • A-RHOM: one declaration covers every round.
  • A-SEQ: the declared order of measurements and messages within a round, and each measuring party completing one round's measurement before the next round's.
  • A-LAB: no timing or synchronisation signal reveals a party's records, and only the declared inputs influence a measurement.
  • A-FIXED: the number of rounds and the acceptance test are fixed before the run.
  • A-ALPHABET: all n rounds are in the record (the acceptance test is evaluated on all n rounds); a measured round missing from it, a lost time tag or no-click bin included, leaves the counts wrong and is a security matter under A-SPEC and A-CONFORM.

Protocol

  1. Rounds: The protocol runs n = 10,000 rounds. See What a round is above. Record: /payload/config/rounds.
  2. Source: In every round the trusted source emits one signal of 4 ((Z,0), (Z,1), (X,0), (X,1)); see Source below. Record: /payload/compiled/source.
  3. Measurement: Each round is measured at Bob's station (declared-finite-povm); see the stations below. Record: /payload/stages/receiver_construction.
  4. Public choices: Alice draws a public choice: Z with probability 0.5, X with probability 0.5. At Bob's station, a public choice is drawn: Z with probability 0.5, X with probability 0.5. Record: /payload/compiled/source/public_choices.
  5. Announcements: Alice announces one of Z, (X,0), (X,1); Bob announces one of Z, (X,0), (X,1). Each announcement is computed from the announcing party's own readout (the record's announcement tables), and A-SEQ states the order within a round: every party's measurement, then the round's public messages. So the analysis assumes that no announcement, a basis included, comes before a measurement of its round; you vouch for this under A-SEQ. Record: /payload/compiled/public/announce_alice.
  6. Sifting and key map: A round gives a raw key bit when its announcements pass sifting: 4 of the 16 combinations of signal and readouts map to a key bit, the rest are discarded. Alice holds the key over the alphabet 0, 1. Record: /payload/compiled/public/key_map.
  7. Acceptance test: The parties estimate the acceptance statistics on the whole run and abort unless they pass; see Acceptance test below. Record: /payload/stages/acceptance_construction.
  8. Error correction: One-way error correction; its transcript leaks λEC = 0 bits, which the key length deducts. Record: /payload/config/parameters/lambda_ec.
  9. Error verification: The parties compare a hash of the corrected keys (failure probability εEV = 9.31323e-10); the key length deducts 30 bits for it. Record: /payload/stages/key_rate/deductions/error_verification.
  10. Privacy amplification: A two-universal hash shortens the corrected key to ℓ = 1,170 bits, secret except with probability εPA = 9.31323e-10. Record: /payload/stages/key_rate/key_length.

A-LAB in full: its text and what it binds on this run

Whatever a party's role, nothing about its letters, settings, choices, detection results, keys or random numbers leaves its laboratory but the final key, the public messages and, where the party sends with a trusted source, the signals that source emits; timing and auxiliary signals reveal no more. An untrusted source counts as outside every laboratory, even one it is in. The attacker reaches a laboratory only via the systems its declared measurements receive and the public messages. Light sent in to read out a letter, a setting, a choice or a detector state (a Trojan-horse attack, at a receiver as at a modulator), emanations from any device, detector back-flash and anything but the declared input modes influencing a measurement violate this, a clock or trigger line from an untrusted source included; where it sends with a trusted source, so does light seeding or recalibrating its laser.

Glossary

Glossary
  • A (the letter): The report uses the letter A in four ways: party A of the declaration (Alice); system A, the declaration's per-round letter on that party's side; a detector port named A (as among BBM92's ports H, V, D and A); and the prefix of a premise's short id (A-LAB, A-SPEC). Which is meant follows from where it stands. See Definition "The protocol declaration as the MEAT core reads it".
  • acceptance test: The test every run applies to its statistics: each round records one acceptance value, and the run continues only if the frequency of every value lies in an interval (together, the box) around the honest model's prediction. See Definition "The construction map".
  • Alice: The name the report gives party A of the declaration. A party may send, measure, or both: in a prepare-and-measure protocol Alice usually sends, in an entanglement-based one she measures at a station; the run's record says which. Where a premise speaks of Alice's letter or of system A, it means the party the declaration assigns A to: Alice, unless the party partition says otherwise. See Definition "The protocol declaration as the MEAT core reads it".
  • Band-A route: The direct route: a finite measurement declared on one sector, with no optical characterisation and no photon-number reduction. It needs an ideal qubit receiver (A-IDEAL), which no real optical receiver is.
  • binding: A value of this run that an assumption is about, for example the εauth you declared for A-AUTH; shown under the assumption so that you know what exactly you vouch for.
  • Bob: The name the report gives party B, the other of the declaration's two parties. Like Alice, he may send, measure, or both; on most protocols he measures at one or more stations. Which he does on this run is read from its record, which also says which party holds system A. See Definition "The protocol declaration as the MEAT core reads it".
  • budget: An error probability (an ε) that you choose before the run. The secrecy, error-verification and authentication budgets εPA, εEV and εauth make up the security parameter ε. The completeness budget εcomp is not part of ε: it is the largest ε* you allow and bounds only how often an honest run fails the acceptance test. The configuration keys keep the word (completeness_budget). See Corollary "Security of the protocol and its net key".
  • certified bound: The first-order bound formed again at the solver's final points from the declared data, every arithmetic step exact or rigorously enclosed: a lower bound on hlow that rests on the claims and the modelling premises and on no premise about floating-point arithmetic. Where a run reaches it, the key length is computed from it, exactly. See Corollary "Key length from the certified bracket".
  • completeness: How often an honest run, with no attacker and devices behaving as modelled, aborts. It never affects the security parameter ε, which holds for every abort pattern. See Remark "Completeness covers the acceptance test only".
  • composable: The kind of security statement the guarantee is: no test, whatever the attacker knows, tells the run's output from an ideal key exchange with advantage above ε. Later uses of the key build on such a statement, but this contract proves only that separate executions add their ε, not that every later use of the key is covered. See Remark "One execution's security parameter and a reused key".
  • constraint entry: A constraint a declaration places on the states it admits, beyond the declared marginal. A run whose declaration carries an entry you declared is checked by the statistics check unless that check is switched off (the inputs table says whether it ran); entries the compiler or a reduction derives do not by themselves call for it. See Requirement "The check of the acceptance set against the feasible statistics".
  • declared tolerance τ: The ceiling on the defects of the run's own data that the snap may repair before solving.
  • detection efficiency: The probability that a detector clicks on a photon that reaches it.
  • effective status: The lowest review status over a claim and everything it rests on; a claim accepted on its own is only as reviewed as its weakest premise.
  • emitted by: The module of the engine whose result rests on the assumption on this run, with the station it was emitted at (station0, station1, ...).
  • endpoint rule: How the acceptance test sets the ends of each outcome's interval: the exact binomial quantile rule (exact) or the closed-form Bernstein rule (bernstein).
  • estimate: The value of the objective at the point the solver returned. It claims no bound: that point is feasible only within a window, so the estimate need not lie above the true minimum hlow. No key length is computed from it.
  • feasible state: A state the declaration admits: block-diagonal and normalised, with the declared marginal and constraints. hlow is an infimum over the feasible states whose statistics pass the acceptance test.
  • first-order bound: A lower bound on hlow from the tangent planes of the objective at the solver's steps. Its proof is exact, and the minima it uses are bounded from below in exact arithmetic, not taken from the solver; its objective and gradient are computed in floating point with no bound on their numerical error. Stopping early makes it looser, not invalid. The key length uses it where the run is not certified. See Theorem "The estimate and the first-order lower bound".
  • Frank-Wolfe: The solver's iterative method: each step minimises a linear approximation of the objective over the feasible set and moves toward that point. See Theorem "The estimate and the first-order lower bound".
  • generation and test rounds: gen is the acceptance value of a round whose announcements pass sifting, so that it may give key. Where a public test coin exists (as in BBM92) it makes each round a generation round (gen), which may give key, or a test round (test), in which both parties announce their full outcome. Every round of either kind records one acceptance value.
  • geometry (acceptance set): The engine's name for the shape of the acceptance set it built; a box of intervals is a polytope.
  • hlb: The first-order lower bound on hlow: the best bound over the steps that passed the first-order checks. It is proved in exact arithmetic, its linear minima bounded exactly, and computed in floating point, so a computed hlb can exceed hlow. A first-order run computes its key length from max{0, hlb}; a certified run computes it from the certified bound hcert and records hlb beside it. See Theorem "The estimate and the first-order lower bound".
  • hlow: A lower bound on the attacker's per-round uncertainty about the raw key, at the chosen α, over every attack compatible with your devices and with statistics that pass the acceptance test.
  • honest envelope: The set of per-round outcome probabilities an honest run is declared to stay within (A-HON-ENV). With a single honest model, as on most runs, it is that model's one law. See Assumption "Honest rounds inside a declared envelope".
  • honest model: The model of what an honest run looks like. It sets the acceptance test and the expected statistics; it never affects the security parameter ε, which holds for every abort pattern.
  • iid_honest_rounds: The acceptance construction's tag for its honest model. In its simplest form the honest rounds are independent and identically distributed with one declared law (A-HON); A-HON-ENV, where a run lists it, lets each round's law vary inside the declared envelope. See Assumption "Honest i.i.d. rounds".
  • kauth: The bits of pre-shared key the authentication uses per run; the net key gain is ℓ − kauth. See Assumption "Authentication of the classical channel by a keyed scheme".
  • kept (snap block): A snap block is kept where your model gives it exactly on the grid, so the snap changes nothing there; every other block is moved.
  • key length ℓ: The number of secret key bits one run outputs, after deducting error correction, error verification and the finite-size cost of secrecy. See Theorem "Secrecy of the key from the accumulated entropy".
  • key map and sifting: Sifting decides from the public announcements which rounds give key; the key map sends each kept round's readout to a key bit. See Theorem "Announcement locality, sifting and party computability".
  • letter: The per-round value on Alice's side of the declaration (system A): in a prepare-and-measure protocol, the signal she prepares. A declaration with one letter uses no clause a premise makes for two or more letters. See Definition "The protocol declaration as the MEAT core reads it".
  • machine key: The stable identifier under which the engine records an assumption.
  • net key length: The key length minus the kauth bits of pre-shared key the authentication consumed: what the run gains. See Corollary "Security of the protocol and its net key".
  • POVM: A measurement written as one positive operator per outcome; the probability of an outcome is the trace of its operator times the state.
  • QBER: The quantum bit error rate: the fraction of key rounds in which the two parties' raw key bits differ.
  • reference (snap): Your declared receiver model, computed exactly (exact) or known through rigorous rational intervals (enclosed). The snap starts from it where it is exact, and the run hands it beside the snap so that the key length can be computed from it.
  • reference companion: Your receiver model put through the same reductions as the rounded measurement, without that rounding, its rows relaxed outward by their floating-point rounding and the model's intervals. A block not handed is carried rounded; with none handed, it is the reduction's exact construction before its own rounding. The run takes its first-order bound there and never solves it. See Corollary "The reference companion of a reduction instance".
  • review status: A claim's review stage, lowest first: superseded (replaced); draft (not yet through an independent review, sent back by one, or substantively amended since); verified (passed an AI model's adversarial review of the written artefacts, not the author's reasoning; not yet accepted by a person); accepted (by the project's human owner); implemented (accepted, its code too). Not a hardware check.
  • round: One use of the protocol as declared, which records its own outcomes. How a time-tagged system cuts its detection record into rounds (time bins, coincidence windows, how the stations synchronise) is your choice, and your declaration must describe it; What a round is, before the protocol's steps, names premises of this run that the cut bears on.
  • sector: One block of a block-diagonal operator, named by a sector map.
  • setting: A probe setting of a receiver; "off" is the setting with no probe light. A receiver without a probe has this one setting only, so on such a station "setting off" names its one measurement, not a switch. See Definition "Probe declaration".
  • snap: Before solving, the declarer (your instance, or a reduction for what it emits) moves each measurement onto a grid of exact numbers of the same shape. A block your model gives exactly on the grid is kept; every other block is moved, and rests on A-SNAP unless it is evaluated off its snap.
  • source mode: Whether the security analysis trusts the source. A trusted source's declared states enter the proof; an untrusted source is the attacker's, and its honest model only predicts the statistics.
  • squashed target POVM: The finite-dimensional measurement the security proof works with; the reduction proves that analysing it covers your receiver.
  • SR3: Condition (SR3) of the source-replacement certificate: the retention attestation, that the retained system A stays in the laboratory of the party that holds it and is acted on only by that party's declared measurement. It carries no number and nothing decides it; you vouch for it as A-SRC.
  • strict option: The run setting strict_snaps: on, the run refuses wherever a moved block or emission sector would rest on A-SNAP, and reports no key length that rests on it, and the certified evaluation does not fall back to the rounded measurement where your receiver model certifies no point; off, the default, such a block is disclosed. See Requirement "Snaps of a measurement family: kept, or moved and disclosed".
  • transmitter: The engine module that models the source side of the protocol. With a trusted source it carries the source's declared states and their premises (A-ENS, A-SRC, or A-WCP for a decoy source); with an untrusted source it carries no source premise. On every run it carries its part of the sequential round order, A-SEQ.
  • α (Rényi order): A parameter of the proof, not of your device: any value in (1, 2) fixed before the run gives a valid key length, and the choice changes only how long the key is, never its secrecy. See Theorem "Secrecy of the key from the accumulated entropy".
  • ε (security parameter): The bound on how far one run's output can be told from an ideal key exchange: ε = εPA + εEV + 2ε_auth. It covers one execution. See Corollary "Security of the protocol and its net key".
  • ε* (completeness): A bound on the chance that an honest run fails the acceptance test; it covers that test only, not later aborts in error verification or authentication. The completeness budget is the largest ε* you allow. See Theorem "The completeness bound".
  • εauth: The error of the authentication of the classical messages, which you declare, including, for a key from an earlier run, its distance from an ideal key; it is counted twice in ε. Zero asserts a channel that is itself authenticated. See Assumption "Authentication of the classical channel by a keyed scheme".
  • εEV: A bound on the chance that both parties accept the run with different keys; error verification compares a hash of ⌈log₂(1/ε_EV)⌉ bits. See Lemma "Correctness from error verification".
  • εPA: The secrecy error of privacy amplification: how far the key may be from uniformly random and independent of everything the attacker holds. See Theorem "Secrecy of the key from the accumulated entropy".
  • λEC: The number of bits the error-correction transcript reveals; the key length deducts it in full. You declare it; with an estimate file beside the record the report shows how it was chosen. See Assumption "Dedicated key register and one-way reconciliation".
